# セキュリティ確認（2026-10-30）

対象: このリポジトリ、ローカルにある全Git参照の36コミット、ブラウザで使われるSupabase公開API。第三者の成績変更や偽スコアの本番投稿は行っていない。

## 修正済み: 端末識別キーの公開

匿名の公開キーで `scores` の表示列はHTTP 200で読め、`device_key` のみを指定した読み取りもHTTP 200で実データが返った。値そのものはこの文書に記録しない。

リポジトリのRPC定義は端末キーを所有確認に使うため、キーが読めると他人の名前・記録を変更される恐れがある。RLSの行公開だけでは、列の秘密は守れない。

**状態: 2026-10-30に本番へ適用済み。** Supabase SQL Editorから列権限の修正を実行し、anon/authenticatedの `has_column_privilege` が両方falseであることを確認した。成績の追加・更新・削除を行うSQLは実行していない。

適用ファイル: [公開列を制限するSQL](../supabase/migrations/202610300001_hide_device_keys.sql)。テーブルや成績を削除せず、公開するSELECT列だけを制限する。管理者のサービス権限は変更しない。

適用後の確認結果:

`npm run check:ranking-security` で、記録の中身を出力せず匿名APIの読み取り権限を再確認できる。適用後に4項目すべてPASSを確認した。

- 匿名の `device_key` 単独取得と `select=*` はHTTP 401 / PostgreSQLエラー42501で拒否（認証済みの権限拒否は403になり得る）。
- 現行クライアントの表示用列と難易度フィルタ、スコア順・生存時間順は200。
- SQL末尾の `has_column_privilege` がanon/authenticatedの両方でfalse。
- `submit_score` / `rename_player` はどちらもpostgres所有のSECURITY DEFINERで、anonのEXECUTE権限が維持されていることを本番の関数メタデータから確認。
- スコア投稿・名前変更の実データを使う本番試験は未実施。今回のSQLはSELECT権限のみを変更し、RPCの定義・実行権限を変更していない。通常プレイ時の確認を残す。

**公開列を閉じても、既に取得された可能性のあるキーは失効しない。** 悪用の有無は今回の確認では分からない。次段階は匿名認証等の本人確認へ切り替え、所有権移行・旧キーの失効を設計する。購入権限・決済にはこの仕組みを使わない。

## 残るランキング不正対策の限界

- スコアはブラウザが計算しRPCへ送る。制約内の偽スコアは作れてしまう。RPC経由だから安全とは言えない。
- UUIDを作り直せば別端末を装えるため、1端末1枠や端末別の15秒制限では大量投稿を防げない。
- 公開DBの制約・RLSポリシー全文・関数権限・ログ・ストレージ等の管理画面監査は完了していない。文書にあるSQLと本番が一致する保証はない。
- サーバーでのプレイ検証、認証、レート制限、運用上の削除基準が今後の対策。オンライン対戦を作る必要はなく、ランキング投稿だけの検証層でもよい。

## リポジトリ側で修正した点

- localStorageが禁止された全利用者に同じUUIDを割り当てるフォールバックを廃止。セッションごとのランダムキーを使う。
- 名前変更APIの失敗を検出し、通信に10秒タイムアウトを設ける。
- 送信名の制御文字と長さを整え、クエリの難易度をURLエンコードする。これらはサーバー側検証の代わりにはならない。
- `.env` 系をGit対象から除外し、公開用の設定例だけを残す。
- CIでテスト・ビルド・high以上の依存監査、Dependabotによる更新通知。
- 解析は許可前にタグを読み込まず、イベントの送信項目を限定する。

## 確認できた点と範囲

- `sb_publishable_...` はブラウザ用公開キーであり、単にコードにあること自体は秘密情報の漏洩ではない。安全性はDB側の権限に依存する。
- ランキングの名前はHTMLエスケープされて描画されている。
- `npm audit` は今回実行時点で0件。新たな脆弱性が発見されない保証ではない。
- 36コミットの差分に対し、Supabase secret形式・JWT形式・GitHub token形式・秘密鍵ヘッダーのパターンを照合し、候補はなかった。全種類の秘密情報を検出したわけではなく、GitHubにしかない削除ブランチ等も対象外。
