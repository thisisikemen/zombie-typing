# アカウント・成長要素・スキン販売の検討

後続の本人要望で、登録端末のVS自己ベストも含める任意ログインの実装へ進んだ。現在の確定仕様・公開状況は [ACCOUNTS.md](ACCOUNTS.md) を優先する。以下は当初の検討記録。

更新: 2026-10-31。実装前の提案。ユーザーの追加方針は、端末をまたぐアカウント、将来の購入スキン、抽選要素、タイピングの上達と再挑戦がつながる一人プレイ。スキン販売は早くても約1か月後、オンライン対戦は先の判断とする。

## 判断

アカウントと所有権の設計は今始める。最初の実装は任意ログインと個人記録の同期までとし、決済や有料抽選を一度に導入しない。ログイン前でもすぐ遊べる状態を維持する。

現在のCloudflare静的配信とSupabaseを継続できる。認証にはSupabase Auth、本人のデータへのアクセス制限にはRLSを使う。将来、決済確認とスキン付与にSupabase Edge Functions等を追加する。VPSや独自の認証サーバー、大規模なホスティング移転は必要条件ではない。

## 現状の根拠

- `src/ui/ranking.ts`: localStorageのUUIDを `p_device_key` として公開RPCへ渡す。ログインセッションは使っていない。別端末に自動で同じ所有者が復元される仕組みはない。
- `src/ui/store.ts`: 自己ベスト、自己ベスト対戦の記録、音量等の設定は端末内保存。
- `src/core/game.ts`: 10コンボごとのボーナスと、回復・シールド・オーバーチャージの効果を実装済み。現在の採用効果は `src/config.ts` の `BONUS.effect = 'heal'`。他の効果が公開プレイで有効になっているとは扱わない。
- エナジーは現在、HPの超過回復と被弾吸収に使う。必殺技のゲージへ転用すると既存の防御・スコアバランスを変えるため、別ゲージで試す案を第一候補にする。

## 最初のアカウント機能

1. ゲストは従来どおり端末内保存で遊べる。遊ぶ前の登録を必須にしない。ゲスト全員に自動でAuthアカウントを作る方式も初期段階では採らない。
2. 「記録を他の端末でも使う」から任意ログイン。最初の候補はGoogleログイン。公開にはGoogle側のOAuth設定とSupabase側の設定が必要で、既存の設定状況は実装時に確認する。
3. 表示名、モード・難易度別の自己ベスト、無料スキンの装備状態を同期する。端末ごとの音量等はローカルに残す。入力時刻配列を持つ自己ベスト対戦は保存量と競合処理を確認し、初回の同期対象から外す案とする。
4. 初回ログインで「この端末の記録を取り込む」を案内する。インポートした個人ベストは本人が編集できるデータとして扱い、購入権限・報酬・検証済みランキングの根拠にはしない。
5. 通信失敗時も遊べる。未同期を表示し、再送は更新ID等で二重反映を防ぐ。同時端末で自己ベストはモードの比較指標で統合し、表示名・装備は更新番号で競合を処理する。
6. ログアウト・別ユーザーへの切り替えで、前の人の記録や装備を次の人へ同期しない。アカウント別キャッシュとゲストの保存領域を分ける。アカウント削除・復旧の導線も公開条件に含める。

メールによるログインも選択肢だが、Supabase標準のメール送信は一般向け本番配信に使わず、独自SMTPを用意する必要がある。Googleログインも外部設定が不要になるわけではない。

## データと権限の境界

以下は論理設計であり、適用できるSQLではない。本番のスキーマ全体と現在のRPC定義を確認してからマイグレーションを作る。

|データ|所有者・更新者|公開範囲|
|---|---|---|
|認証情報|Supabase Auth|公開ランキングにメールやトークンを出さない|
|表示名・個人ベスト|ログイン本人。`auth.uid()`で制限|本人の同期APIと公開プロフィールを分離|
|ランキング|認証済み投稿API。`user_id`はトークンから決定|表示名・成績等の必要な列だけ|
|スキン商品一覧|運営|公開で読み取り可能|
|スキン所有権|検証済み決済・運営付与・検証済み報酬処理だけ|本人の読み取りのみ。本人にも追加・変更権限を与えない|
|スキン装備|ログイン本人|サーバーで所有確認。許可された項目だけ変更可能|
|注文・決済イベント|サーバー側の決済処理|ブラウザから作成・成功状態への変更を許可しない|

購入済み情報をlocalStorageや本人が編集できるAuthの `user_metadata` に保存して権限判定しない。所有権はDBを正とし、装備APIも確認する。スキン画像自体のコピー防止と、購入権限の保護は別の問題。

旧端末UUIDは過去に公開されていた可能性があるため、UUIDを知っているだけで旧ランキングの本人だと断定しない。旧ランキングは保持し、アカウント版ランキングの世代を分ける案を推奨する。既存ユーザーの記録を一括削除しない。

ログインはユーザー単位の制限や管理に役立つが、ブラウザから送るスコアの正しさは保証しない。公式ランキングやスコア連動の景品には、プレイID、ルールの版、サーバーでの時間・入力・成績検証等を段階的に追加する。単純な上限チェックだけで不正防止完了とは扱わない。

## スキン販売の順序

最初は無料スキンで、別端末での所有・装備の復元を確認する。その後、内容と価格が分かる固定商品の販売を小さく試す。強さやランキングの有利不利を販売せず、見た目中心を推奨する。

決済はホスト型Checkoutを候補にする。購入完了画面への遷移だけでは付与せず、サーバーで署名を検証した決済イベントを処理する。注文とログインユーザーをサーバーで対応させ、二重配信・遅延・順不同・返金時にも所有権が壊れない設計とテストを用意する。決済サービスの利用可否や条件は商品内容が決まってから確認する。

有料ガチャは初回の販売対象から外す提案。抽選確率、重複、確定入手の仕組み、購入履歴、未成年への対応、返金・問い合わせ等の運営設計を先に詰める。導入判断時には対象地域の規則と決済事業者の条件を別途確認する。この文書は有料ガチャの適法性を判断していない。

## 一人プレイの継続要素

目指す体験は「狙う → 正確に打つ → 技が近づく → 自分のタイミングで使う → 自己ベストと上達を実感 → もう一回」。初回の試作は以下の一つに絞る。

- 正打・撃破で専用ゲージが貯まり、満タンでグレネードを1回使える。
- ミスでコンボは切れてもゲージ全消失にはせず、初心者も発動を体験できるよう調整する。
- 発動は専用キー等で誤入力と区別する。視覚効果・音・振動感は調整可能にし、激しい点滅や文字の隠れを避ける。
- 自動撃破中にも打つ対象を残し、スコア上昇を実入力の速度・正確さと区別する。WPMや正確率を自動撃破で水増ししない。
- 現行モードと分けた実験モードで検証し、既存ランキングに異なるルールのスコアを混ぜない。

短い達成目標、無料の見た目アンロック、自己ベストとの差を次の候補とする。長時間の連続プレイや離脱への罰より、1プレイの満足度と翌日また遊ぶ理由を優先する。演出だけで継続や学習効果が上がると断定せず、再挑戦率・翌日再訪・正確率・同条件の入力速度・初心者の終了率で評価する。

## 進める順序と検証条件

1. 独自ドメインのHTTPSを確認してログインの戻り先を確定する。DNS待ちの間にもAuth設計・コードの分離・RLSのテスト準備は進められる。
2. 任意ログインと個人ベスト同期を開発用環境で実装。本人Aから本人Bの読取・更新が拒否されること、ログアウト、端末をまたぐ復元、同期失敗、既存記録の保持を検証して公開する。
3. 別の実験モードでゲージと技を試作。新機能の成績は現行ランキングへ送らない。
4. 無料スキンの所有・装備のサーバー管理を検証。
5. 固定スキン販売を決済のテスト環境で実装し、署名不正・偽の成功リクエスト・二重通知・返金を検証。本番決済は別の公開判断とする。

本検討ではログイン・DB変更・決済・新しい技の本番反映は行っていない。
